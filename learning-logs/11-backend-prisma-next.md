## This is NOT classic Prisma

If you've seen Prisma before, unlearn some of it. Classic Prisma =
`schema.prisma` + a `generator` block + `npx prisma generate` + `import { PrismaClient }
from "@prisma/client"`. **Prisma ORM for Postgres (v8, "Prisma Next")** replaces that
with a *contract*.

| Classic Prisma | Prisma Next (this repo) |
|----------------|------------------------|
| `schema.prisma` | `src/prisma/contract.prisma` |
| `prisma generate` -> `node_modules/.prisma/client` | `prisma contract emit` -> `contract.json` + `contract.d.ts` (checked into the repo) |
| `new PrismaClient()` | `postgres<Contract>({ contractJson, url })` in `src/prisma/db.ts` |
| `prisma migrate dev` | `prisma db init` / `prisma migration status` |
| `prisma.user.findUnique(...)` | `db.orm.public.User.where({...}).first()` |

The npm packages: `prisma` (CLI, `^8.0.0-rc`), `@prisma/orm-postgres` (runtime + config,
`^8.0.0-rc`), `@prisma/cli-engine` (used by `prisma.config.ts`). All release candidates -
expect rough edges.

## The files

### `src/prisma/contract.prisma` - YOUR schema

This is where you declare models. **It currently holds the starter sample, not the
school domain:**

```prisma
// use prisma-next

model User {
  id        Int      @id @default(autoincrement())
  email     String   @unique
  username  String?
  name      String?
  posts     Post[]
  createdAt TimestamptzString @default(now())
  updatedAt temporal.updatedAtString()
}

model Post {
  id        Int      @id @default(autoincrement())
  title     String
  content   String?
  author    User     @relation(fields: [authorId], references: [id])
  authorId  Int
  createdAt TimestamptzString @default(now())
  updatedAt temporal.updatedAtString()
}
```

Syntax notes vs classic Prisma:
- `@id @default(autoincrement())`, `String?` (nullable), `@unique`, `@relation(...)` -
  same as before.
- `TimestamptzString @default(now())` - Prisma Next exposes Postgres types more directly;
  timestamps come back as ISO strings by default.
- `temporal.updatedAtString()` - a helper that auto-sets the column on create and update
  (it shows up in `contract.d.ts` as a `timestampNow` generator on both `onCreate` and
  `onUpdate`).

### `src/prisma/contract.json` - the compiled contract

Generated by `prisma contract emit`. It is to your schema what `package-lock.json` is to
`package.json`: the exact, resolved description of every model, column, index, and
foreign key. **Commit it.** Regenerate whenever `contract.prisma` changes.

### `src/prisma/contract.d.ts` - generated types

Also from `prisma contract emit`. ~630 lines of TypeScript that give your editor
autocomplete for every table, column, relation, and the exact return type of every
query. First line: `GENERATED FILE - DO NOT EDIT`. You never touch this; you read the
types it produces through `db`.

### `src/prisma/db.ts` - the client

```ts
import 'dotenv/config';
import postgres from '@prisma/orm-postgres/runtime';
import type { Contract } from './contract.d';
import contractJson from './contract.json' with { type: 'json' };

export const db = postgres<Contract>({
  contractJson,
  url: process.env['DATABASE_URL']!,
});
```

- `import 'dotenv/config'` loads `.env` so `DATABASE_URL` is available.
- `postgres<Contract>(...)` builds the typed client. `<Contract>` is the entire schema as
  a type - that is what makes queries type-safe.
- `contractJson` is the runtime description; `Contract` (from `contract.d.ts`) is the
  compile-time description. Both are passed/used.
- `import ... with { type: 'json' }` is the standard JSON import (needs
  `resolveJsonModule` in `tsconfig.json`, which the Prisma Setup commit added).
- `process.env['DATABASE_URL']!` - the `!` asserts "this is definitely defined" to
  TypeScript. If `.env` is missing it, you get a runtime failure, not a type error.

**Import it as `import { db } from "@/prisma/db"` and only in server code** (Server
Components, Server Actions, route handlers) - never in a `"use client"` file.

### `prisma.config.ts` - CLI configuration

```ts
export default definePrismaConfig({
  orm: ormConfig({
    contract: "./src/prisma/contract.prisma",
    db: { connection: process.env['DATABASE_URL']! },
  }),
});
```

Tells the `prisma` CLI where the contract lives and how to reach the database. ESM
because `package.json` has `"type": "module"`.

### `.env` / `.env.example`

```
DATABASE_URL="postgresql://user:password@localhost:5432/mydb"
```

`.env` is git-ignored; `.env.example` is the committed template. **Postgres 15+ is
required.**

### `package.json` additions

- `"postinstall": "prisma skills sync || exit 0"` - after every `npm install`, Prisma
  copies its AI-assistant skill docs into `.agents/ .claude/ .cursor/ .devin/` (all now
  git-ignored). The `|| exit 0` stops a sync failure from breaking `npm install`.
- `"contract:emit": "prisma contract emit"` - shortcut to regenerate
  `contract.json` + `contract.d.ts`.

## How you will query (from `prisma-next.md`)

```ts
import { db } from "@/prisma/db";

const user = await db.orm.public.User
  .where({ email: "alice@example.com" })
  .first();
// user: { id, email, username, name, createdAt, updatedAt } | null  -- fully typed
```

`db.orm.<namespace>.<Model>` - `public` is the default Postgres schema/namespace.

## The standard workflow

1. Edit `src/prisma/contract.prisma`.
2. `npx prisma contract emit` (or `npm run contract:emit`) - updates `contract.json` +
   `contract.d.ts`. In a Next.js project the Prisma plugin can do this automatically on
   dev, but running it by hand always works.
3. `npx prisma db init` - creates the tables in the database.
4. `npx prisma migration status` - check what's applied.
5. Query with `db` in server code.
